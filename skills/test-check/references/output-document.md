# ドキュメント

## 現行の内容を書く

- 想定読者が必要な参照を含めて理解・判断・実行できる内容を書く。
- 現在の仕様、手順、責任、条件を直接記述する。
- 編集作業の説明や、過去の案への打ち消しを本文に残さない。
- 変更の経緯と理由は、原則としてコミットログやPRに残す。
- 過去の内容を残すのは、移行、互換性、判断理由の保存など、読む目的がある場合に限る。現行の説明と混在させず、適切な節や別文書に置く。
- 禁止事項、制限、非対応の条件は、読者の行動に必要な場合に明記する。否定語を肯定形に変えること自体を目的にしない。

| 避けたい記述 | 現行の内容を示す記述 |
|---|---|
| 旧CSVは使いません。APIに変更しました | データはAPIから取得する |
| 前案の管理画面は対象外です | 管理者は設定ファイルで接続先を指定する |
| 自動再実行は入れません | 失敗したジョブは、担当者が原因を確認して再実行する |

書き換えに必要な仕様が不明な場合は、推測で補わず確認する。

未確認事項から、新しい禁止・承認・停止・再実行の条件を確定しない。資料にない操作方法や判断条件は確認事項として示す。改善案を求められた場合も、提案と現行手順を区別する。

## 情報量と構成を調整する

- 必要な背景、条件、例外を残す。短さだけを優先して省略しない。
- 概要、本文、補足を分け、読者が必要な箇所を選んで読めるようにする。
- 同じ説明を複数箇所に複製せず、必要に応じて参照先を示す。
- 用語と文体を統一する。正式な用語は必要に応じて定義する。
- 抽象的な意義や自己評価より、対象、動作、条件、結果を書く。
- 見出しは内容を探すために付ける。装飾や項目数を揃えるために節を増やさない。
- 決定事項、提案、未決事項を区別する。

Issueは依頼内容と完了条件を、PR本文は問題・最終変更・検証結果を中心にする。コミットログ・PR・変更履歴・移行文書では、記録の目的に応じて変更経緯を残せる。記録先を案内する指示から、commitや外部投稿を自動で行う権限は生じない。

コミットログには変更内容と必要な理由を記す。元メモの抽象的な言い回しや、それをどう言い換えたかの説明を再掲して膨らませない。
