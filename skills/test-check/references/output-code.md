# コード

- 変更するファイルと周囲の命名、構造、エラー処理、コメントの書き方に合わせる。
- 今回の要件に必要な変更に絞る。関係のない整理を混ぜない。
- 既存の処理を確認し、同じ役割の関数や仕組みを重複して作らない。
- 将来使うかもしれないという理由だけで、抽象化、設定、依存関係を追加しない。
- 型エラーを隠すための型指定、失敗を隠す例外処理、根拠のない既定値を追加しない。
- 入力検証や例外処理は、入力元、契約、失敗時の扱いを確認して判断する。
- コードを読めば分かるコメントや、処理を順に読み上げるコメントを追加しない。
- 業務上の理由、制約、回避策、削除すると再発する問題を説明するコメントは残す。必要なIssue番号やバージョン情報も保持する。
- 削除した実装をコメントアウトして残さない。変更の経緯はコミットログに記録する。
- コメントは現在の挙動を説明する。「以前はこうだった」「この処理は削除した」などの履歴は、保守上必要な場合だけ残す。
- 試行錯誤で追加した不要な処理、デバッグ出力、使われなくなった分岐を最終差分に残さない。
- 文章上の好みだけで、公開APIや既存の識別子を変更しない。

コードを変更した場合は、変更に応じた動作確認を行う。レビューではこれらを確認観点として使い、修正は依頼範囲に従う。
