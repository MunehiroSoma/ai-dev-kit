# 検証と完了判定

静的レビューと実行検証を区別し、変更の受入条件を満たした証拠を残す。すべての変更に同じテストや記録ファイルを要求しない。

1. 変更内容、受入条件、リポジトリの検証規約・既存コマンドを確認する。コマンドを推測して実行せず、設定やスクリプトから選ぶ。
2. 影響に応じて、既存テスト、lint、型検査、整形のチェックモード、手動再現から必要なものを選ぶ。単純な文言変更にDBや外部APIの検証を追加しない。
3. 動作変更には正常系に加えて、今回影響する不正入力・境界・外部障害・並行性等を選ぶ。モックだけで確認できない契約やDB制約は、利用可能な安全な検証環境で確認する。
4. 実行前に対象環境を確かめる。本番データ変更や外部への実送信は検証依頼だけで許可されたと解釈しない。準備が不足する場合は未確認として理由を残す。
5. 成否、入力と観測結果、適用外、未実施、失敗を分ける。失敗を隠して完了にせず、必要条件が未確認なら残件として報告する。成功後に理由なく同じ検証を繰り返さない。

## 記録

プロジェクトの記録先を優先する。継続的な証跡が必要、または記録を依頼された場合は既存記録を更新し、ない場合は `docs/tests/TC_機能名.md` など合意された場所に保存する。小さい確認はチャットやPR本文で十分なら新規ファイルを増やさない。

記録には次を含める。

- 対象変更・受入条件、実施日、対象環境（機密情報は含めない）
- 実際のコマンドまたは再現手順、入力と観測結果
- 実施済みの正常系・異常系、適用外の理由
- 未確認・失敗とその影響、完了判定

テスト実行、コードレビュー、リリース、本番での確認はそれぞれ区別して報告する。このスキルは公開・デプロイを行わない。

## 記述ルール

記述・編集前に[共通ルール](references/output-common.md)を読み、出力内容に応じて[応答](references/output-response.md)・[ドキュメント](references/output-document.md)・[コード](references/output-code.md)の該当ルールを読む。チャット内の仕様書もドキュメントとして扱い、複数対象があれば各部分に適用する。ユーザー指定・リポジトリ規約・必要なテンプレートを尊重する。

検証結果の返答は応答、保存するテスト記録はドキュメント、追加・修正するテスト実装はコードとして扱う。未確認事項や失敗の影響は判断に必要な情報として残す。

提出前に、不要な説明・反復・装飾と、過去案への打ち消しを確認する。必要な条件・根拠・不確実性・挙動を保持し、コード変更には変更に応じた動作確認を行う。

## 研修モード

「研修モード」が明示された場合だけ、タスクの最後に良かった点・使いにくかった点・改善提案・今すぐ更新するかをまとめて1回確認する。通常は振り返り質問を出さない。

同じタスクで複数スキルを使っても、振り返りは全体の終了時に1回だけ行い、途中や各スキルの終了ごとに繰り返さない。
