# ブランチ準備の互換入口

既存の `/new-feature feature/example`（Codex では `$new-feature`）を引き続き使えるようにする。

- `start` が現在の環境で利用可能なら、指定された目的・ブランチ名・開始点を引き継ぎ、Issue を選ばない経路へ委譲する。未導入の `start` を探し続けたり、勝手にインストールしたりしない。
- 単体導入の場合は、以下の最小手順で同じ結果を作る。

## 単体での手順

1. リポジトリ、現在ブランチ、未コミット・ステージ済み・未追跡の変更、既存 worktree を確認する。適切な既存作業ブランチがあれば再利用する。
2. ユーザー指定の開始点を優先する。なければ対象 remote の既定ブランチを確認し、必要に応じて fetch する。`main` / `origin` を固定しない。
3. 既存作業を自動で stash・破棄・移動しない。dirty な作業場所や別 worktree が使うブランチを切り替えず、適切な既存 worktree または新しい別 worktree で準備する。必要な未コミット変更の引継ぎが不明ならそこだけ確認する。
4. 希望名とリポジトリ規約に従ってブランチを用意する。同名ブランチを reset しない。作業パス、ブランチ、開始点を報告する。

Issue 作成・実装・PR・マージは、それぞれ依頼された範囲でのみ行う。

## 記述ルール

記述・編集前に[共通ルール](references/output-common.md)を読み、出力内容に応じて[応答](references/output-response.md)・[ドキュメント](references/output-document.md)・[コード](references/output-code.md)の該当ルールを読む。チャット内の仕様書もドキュメントとして扱い、複数対象があれば各部分に適用する。ユーザー指定・リポジトリ規約・必要なテンプレートを尊重する。

ブランチ準備の報告は応答として扱う。委譲先でも出力対象に応じたルールを適用する。

提出前に、不要な説明・反復・装飾と、過去案への打ち消しを確認する。必要な条件・根拠・不確実性・挙動を保持し、コード変更には変更に応じた動作確認を行う。

## 研修モード

「研修モード」が明示されたときだけ、タスク終了時に良かった点・使いにくかった点・改善提案・今すぐ更新するかを1回確認する。`start` に委譲した場合は重複して聞かない。通常は振り返り質問を出さない。

同じタスクで複数スキルを使っても、振り返りは全体の終了時に1回だけ行い、途中や各スキルの終了ごとに繰り返さない。
