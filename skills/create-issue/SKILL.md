# GitHub Issue を作る

対象リポジトリと既存 Issue を確認し、重複を避けてタイトル・ラベル・本文を準備する。認証済みの接続ツールまたは `gh` を使い、勝手にツール導入や認証変更をしない。

## 種別と内容

リポジトリの Issue テンプレート・運用規約を優先する。ない場合は次を基準にする。

| 種別 | 粒度 | 本文に必要な内容 |
|---|---|---|
| Task | 独立して確認・完了できる作業単位 | 目的、作業内容、観測できる完了条件、親 Issue があれば関連 |
| Bug | 1つの不具合または同じ原因の症状 | 影響、再現手順、期待と実際の結果、根拠のファイル/行番号、関連 Issue |
| Epic | 複数 Task で達成する目的 | 全体の目的・完了条件、子 Issue、依存関係 |

ラベルは存在と意味を確認して選ぶ。固有の優先度ラベルや1〜3日という日数を全リポジトリへ強制しない。未確定の内容を確定事項として書かない。

## 作成

1. タイトル、ラベル、本文を提示する。ユーザーがまだ確定内容を承認していない場合は、作成前に内容の確認を受ける。既に具体的な内容と作成が承認済みなら再承認を求めない。
2. 対象リポジトリを明示して作成する。複数行本文は構造化引数または一時ファイルと `--body-file` を使い、シェルで本文を評価させない。PowerShell に Bash の行継続をそのまま渡さない。
3. 成功した Issue の URL を返す。結果不明の失敗では既存 Issue を検索してから再試行し、重複作成を避ける。

追加コメント、担当者設定、外部通知は依頼された範囲でのみ行う。

## 記述ルール

記述・編集前に[共通ルール](references/output-common.md)を読み、出力内容に応じて[応答](references/output-response.md)・[ドキュメント](references/output-document.md)・[コード](references/output-code.md)の該当ルールを読む。チャット内の仕様書もドキュメントとして扱い、複数対象があれば各部分に適用する。ユーザー指定・リポジトリ規約・必要なテンプレートを尊重する。

相談・作成結果は応答、Issueのタイトルと本文はドキュメントとして扱う。

提出前に、不要な説明・反復・装飾と、過去案への打ち消しを確認する。必要な条件・根拠・不確実性・挙動を保持し、コード変更には変更に応じた動作確認を行う。

## 研修モード

「研修モード」が明示された場合だけ、タスクの最後に良かった点・使いにくかった点・改善提案・今すぐ更新するかをまとめて1回確認する。通常は振り返り質問や見送り理由の投稿を要求しない。

同じタスクで複数スキルを使っても、振り返りは全体の終了時に1回だけ行い、途中や各スキルの終了ごとに繰り返さない。
