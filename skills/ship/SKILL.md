# 変更を PR として提出する

`/ship`（Codex は `$ship`）は **commit → push → PR 作成または更新** まで。マージ、ブランチ削除、基準ブランチへの checkout / pull は行わない。

## 対象と権限を確定する

- 明示された対象変更・リポジトリ・公開範囲を守る。commit / push / PR の依頼が既に明確なら同じ許可を聞き直さない。レビューやローカル保存だけの依頼を公開の許可と解釈しない。
- 現在のブランチ、remote、dirty 状態、ステージ済み差分、未追跡ファイル、既存 worktree、既存 PR を確認する。対象外の変更・ステージ内容を混ぜず、自動 stash・破棄・全件 staging をしない。
- PR の head と base を明示的に決める。ユーザー指定と既存 PR を優先し、親ブランチを使う作業ではその親を base にする。指定がなければ対象 remote の既定ブランチを確認する。`main` / `origin` を固定しない。
- 基準ブランチ上なら作業ブランチを準備する。共有 worktree を切り替えず、既存の適切な作業場所を再利用する。対象差分だけをコミットできない場合は、変更を維持して必要な分離方法を確認する。

## 提出する

ホスト別の公式手順が利用可能なら、[公式手順の選択](references/providers.md) を読み、このスキルの対象限定・PR 停止条件を伝えて利用する。未導入ならインストールせず、次の小さい代替で進める。

1. リポジトリの規約・PR テンプレート・実在する検証コマンドを確認する。変更に応じた検証を行い、実施済み・未実施・失敗を区別する。既知の失敗を伏せて提出しない。失敗状態での draft 提出が依頼されていればその範囲で進める。
2. 対象差分だけを stage・commit する。無関係な staged 変更を含めない。既存コミットの提出だけなら空コミットを作らない。コミット直前に差分を確認する。
3. 対象 remote と head に通常の push を行う。失敗時に無関係な pull・rebase・force push を追加せず、原因と未完了操作を示す。
4. 同じ head の PR があるならそれを更新し、base と draft / ready 状態を勝手に変えない。新規なら明示した base / head で draft PR を作成する（ready の指定があれば従う）。既存 PR の base が今回の意図と異なる場合は作成・更新前に確認する。
5. PR 本文は問題、最終的な変更、関連 Issue、意味のある検証結果を簡潔に記す。Issue は本当に解決する場合だけ `Closes` を使う。複数行本文は一時ファイルと `--body-file` 等を使い、シェルで本文を評価させない。利用環境に PR 添付機能があれば作成・更新した PR を添付する。

CLI を使う場合は `gh` の存在と認証を確認する。利用可能な接続ツールでも同じ対象・権限を守る。ツールや認証がなければ具体的な不足を伝え、勝手に導入・認証変更しない。

最後に PR URL、head / base、検証結果、未完了事項を報告して終了する。再実行時も既存 PR を確認し、重複作成しない。

## 記述ルール

記述・編集前に[共通ルール](references/output-common.md)を読み、出力内容に応じて[応答](references/output-response.md)・[ドキュメント](references/output-document.md)・[コード](references/output-code.md)の該当ルールを読む。チャット内の仕様書もドキュメントとして扱い、複数対象があれば各部分に適用する。ユーザー指定・リポジトリ規約・必要なテンプレートを尊重する。

提出結果は応答、PR本文はドキュメントとして扱う。コミットログには変更内容と必要な経緯・理由を残す。

提出前に、不要な説明・反復・装飾と、過去案への打ち消しを確認する。必要な条件・根拠・不確実性・挙動を保持し、コード変更には変更に応じた動作確認を行う。

## 研修モード

「研修モード」が明示された場合だけ、タスクの最後に良かった点・使いにくかった点・改善提案・今すぐ更新するかをまとめて1回確認する。通常は振り返り質問を出さない。

同じタスクで複数スキルを使っても、振り返りは全体の終了時に1回だけ行い、途中や各スキルの終了ごとに繰り返さない。
