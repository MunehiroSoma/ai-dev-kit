# 作業ブランチを同期する

旧来の `/sync-main`（Codex は `$sync-main`）という名前を維持するが、基準ブランチを `main` に固定しない。

1. リポジトリ、現在ブランチと HEAD、dirty 状態、進行中の merge / rebase、既存 worktree、追跡先を確認する。進行中の操作があれば新しい同期を重ねない。
2. ユーザー指定の remote・基準ブランチ・取り込み方式を優先する。未指定なら対象 remote の既定ブランチとリポジトリ方針を確認する。複数候補で意味が変わる場合だけ確認する。
3. fetch で更新を取得し、作業ブランチとの差分・分岐を確認する。共有のローカル基準ブランチへ checkout / pull する必要はない。
4. dirty な作業を自動 stash・破棄しない。作業変更を維持したまま安全に取り込めない場合は同期前の状態と理由を示して止める。別 worktree が使用するブランチを変更しない。
5. 未公開で共有されていない作業ブランチは、指定・方針に従って取得済みの基準 ref へ rebase できる。公開済み・共有ブランチの履歴書換えは既存の承認がある場合だけ行い、なければ merge 等の選択を確認する。基準ブランチ自身を更新する場合は fast-forward のみとし、分岐していれば止める。
6. 競合時は競合ファイルと停止状態を示す。依頼範囲で解決できるものだけ解決し、不明な業務判断や変更破棄を独断で行わない。元の HEAD と再開・中止の方法を残す。

成功時は取り込んだ基準 ref、結果の HEAD、作業状態、必要な検証結果を報告する。push、force push、ブランチ削除はこのスキルの終了条件に含めない。

## 記述ルール

記述・編集前に[共通ルール](references/output-common.md)を読み、出力内容に応じて[応答](references/output-response.md)・[ドキュメント](references/output-document.md)・[コード](references/output-code.md)の該当ルールを読む。チャット内の仕様書もドキュメントとして扱い、複数対象があれば各部分に適用する。ユーザー指定・リポジトリ規約・必要なテンプレートを尊重する。

同期結果・競合状況の報告は応答、競合解消で編集する実装はコードとして扱う。

提出前に、不要な説明・反復・装飾と、過去案への打ち消しを確認する。必要な条件・根拠・不確実性・挙動を保持し、コード変更には変更に応じた動作確認を行う。

## 研修モード

「研修モード」が明示された場合だけ、タスクの最後に良かった点・使いにくかった点・改善提案・今すぐ更新するかをまとめて1回確認する。通常は振り返り質問を出さない。

同じタスクで複数スキルを使っても、振り返りは全体の終了時に1回だけ行い、途中や各スキルの終了ごとに繰り返さない。
