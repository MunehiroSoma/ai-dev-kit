# 作業を開始する

Issue の内容と作業場所を確認し、実装に着手できる状態を作る。
Claude Code は `/start`（プラグイン導入時は `/ai-dev-kit:start`）、Codex は `$start`。Issue 番号、作業内容、希望ブランチ名を渡せる。

## 対象を決める

- Issue が指定済みならその詳細を読む。未指定で Issue から選ぶ依頼なら open な Issue を取得し、候補を示す。すでに会話で決まった対象を再選択させない。
- Issue を使わない依頼なら、指定された作業内容とブランチ名で進める。Issue の作成を必須にしない。
- GitHub 情報は利用可能な接続ツール、または認証済み `gh` で取得する。認証・アクセスが不足する場合はその操作だけを止め、解決に必要な情報を伝える。勝手にインストールや認証変更を行わない。

## ブランチを準備する

1. リポジトリ、現在のブランチ、未コミット・ステージ済み・未追跡の変更、既存 worktree を確認する。すでに適切な作業ブランチなら再利用する。
2. 開始点はユーザー指定を優先する。指定がなければ対象 remote の既定ブランチを確認し、必要なら fetch して開始コミットを決める。`main` / `origin` を固定せず、共有作業ディレクトリで checkout / pull を始めない。
3. 未コミット変更を別ブランチへ持ち込む、stash する、破棄する操作を自動で行わない。他の worktree の使用状況も踏まえ、適切な既存 worktree を使うか、新しいブランチを別 worktree に作る。ユーザーの未コミット変更が作業に必要なら、その引継ぎ方法を確定してから進める。
4. 既存ブランチを reset せず、リポジトリの命名規約に従ってブランチを作る。規約がなければ `feature/`、`fix/`、`docs/` など目的が分かる名前を使う。

準備したパス、ブランチ、開始点、対象 Issue（ある場合）を伝える。開始コメントの投稿は依頼された場合だけ行う。ブランチ準備だけの依頼から実装・PR・マージへ範囲を広げない。

## 記述ルール

記述・編集前に[共通ルール](references/output-common.md)を読み、出力内容に応じて[応答](references/output-response.md)・[ドキュメント](references/output-document.md)・[コード](references/output-code.md)の該当ルールを読む。チャット内の仕様書もドキュメントとして扱い、複数対象があれば各部分に適用する。ユーザー指定・リポジトリ規約・必要なテンプレートを尊重する。

Issue候補とブランチ準備の報告は応答として扱う。

提出前に、不要な説明・反復・装飾と、過去案への打ち消しを確認する。必要な条件・根拠・不確実性・挙動を保持し、コード変更には変更に応じた動作確認を行う。

## 研修モード

ユーザーが「研修モード」を明示した場合だけ、タスクの最後に良かった点・使いにくかった点・改善提案・今すぐスキルを更新するかをまとめて1回確認する。複数スキルを使っても繰り返さない。通常は確認せず、見送り理由の記録や外部投稿も要求しない。

同じタスクで複数スキルを使っても、振り返りは全体の終了時に1回だけ行い、途中や各スキルの終了ごとに繰り返さない。
