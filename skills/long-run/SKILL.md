# 長時間の作業を継続する

目的を達成するまで、不要な確認待ちを挟まずに調査・実装・検証を進める。Full Access など特定の権限設定や、親子ブランチ構成を前提にしない。

## 開始時に揃えること

- 目的、観測できる完了条件、許可された操作範囲、制約を短く整理する。既に決まった内容は再確認しない。予算・期限・停止条件の指定があれば従う。
- 実装する場合は現在ブランチ、変更状態、worktree、開始点を確認し、適切な作業場所を再利用する。`main` 固定の checkout / pull、自動 stash・破棄をしない。新しい場所が必要なら既存変更を保全した別 worktree を使う。
- 開始点は指定を優先し、未指定なら対象 remote の既定ブランチを確認する。親子ブランチは複数の独立作業を統合する必要がある場合だけ使い、使うなら各子の base と親への統合方針を明示する。

## 継続と停止

1. 最短で完了条件を確認できる順に進め、変更に必要な検証を行う。失敗は原因を絞って修正し、同じ操作を無限に再試行しない。
2. マイルストーン、重要な発見、障害、方針変更を簡潔に報告する。長い無応答を避け、実行環境の進捗通知規則に従う。
3. 長い作業や引継ぎが必要な場合は、完了済み・残作業・検証結果・作業パス/ブランチ・次の一手を、利用可能なタスク状態またはプロジェクトの作業メモに残す。再開時は実際のファイル・Git・処理状態と照合する。
4. 低リスクで可逆な判断は依頼範囲内で進める。権限不足、不可逆操作、未確定の業務判断が障害なら、独立して進められる作業を先に行い、必要な点だけまとめて確認する。
5. 完了条件を満たしたら停止する。明示停止・予算上限・解消不能な障害でも作業状態と残件を報告する。外部障害で進めない状態を延々と繰り返さない。

PR 提出が依頼に含まれるなら、利用可能な `ship` または認証済みツールで、対象と base を確認して PR 作成・更新まで行う。自動 merge、ブランチ削除、外部通知は追加しない。将来の自動再開や通知が必要なら、利用者の依頼とホストの機能に従って設定し、文章だけで継続実行を約束しない。

完了した内容、検証した範囲、未解決事項、再開情報がある場合はその場所を報告する。

## 記述ルール

記述・編集前に[共通ルール](references/output-common.md)を読み、出力内容に応じて[応答](references/output-response.md)・[ドキュメント](references/output-document.md)・[コード](references/output-code.md)の該当ルールを読む。チャット内の仕様書もドキュメントとして扱い、複数対象があれば各部分に適用する。ユーザー指定・リポジトリ規約・必要なテンプレートを尊重する。

進捗・完了報告は応答、引継ぎメモや作成文書はドキュメント、実装はコードとして扱う。再開に必要な状態と未完了事項は残す。

提出前に、不要な説明・反復・装飾と、過去案への打ち消しを確認する。必要な条件・根拠・不確実性・挙動を保持し、コード変更には変更に応じた動作確認を行う。

## 研修モード

「研修モード」が明示された場合だけ、タスクの最後に良かった点・使いにくかった点・改善提案・今すぐ更新するかをまとめて1回確認する。途中で他のスキルを使うたびに質問しない。通常は振り返り質問を出さない。

同じタスクで複数スキルを使っても、振り返りは全体の終了時に1回だけ行い、途中や各スキルの終了ごとに繰り返さない。
