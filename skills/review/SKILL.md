# 変更をレビューする

対象の目的・受入条件と差分を照合し、実際に壊れる点を見つける。対象や比較元が曖昧なら、現在の変更・指定 PR・会話から絞り、結論が変わる不明点だけ確認する。

## 手順の選択

利用可能な公式レビュー機能・スキルが対象と権限に合う場合は、[レビュー先の選択](references/providers.md) を読んで優先する。別途指定されたレビュー手順があれば尊重する。未導入なら勝手にインストールせず、以下で完結する。

1. 関連するリポジトリ規約、変更の目的、差分と必要な周辺コードを読む。関係のない全資料を先に読ませない。
2. 正しさ、境界・エラーパス、状態・並行性、入力の信頼境界、影響範囲の順で、変更に該当する観点を選ぶ。
3. 問題ごとに発生条件、根拠のファイルと行、利用者への影響を確認する。推測は推測と明示し、証拠が足りなければ必要な確認を示す。既存仕様や意図した設計との差を、好みだけで不具合扱いしない。
4. 検証が必要なら変更に対応する既存テストや再現方法を選ぶ。外部・本番への書込みを含む確認はレビュー権限から推定しない。静的レビューを実行済みテストとして報告しない。

外部 API のリトライは冪等性と重複実行時の影響を確認する。モック・統合テスト・実環境検証は目的に応じて使い分け、モック化やリトライを一律に必須としない。性能の指摘は想定規模や実際の処理経路で裏付ける。

## 結果

- **Critical**: データ破壊・権限逸脱・主要目的の未達など、提出を止める問題。
- **Should**: 実害があり修正すべき問題。発生条件と影響を添える。
- **Nit**: 好み・軽微な整形。主要な問題と混ぜず、必要なものだけまとめる。

重要な指摘から、ファイル/行、問題、壊れる条件、修正方向を簡潔に示す。最後に確認範囲、未確認事項、判定（承認・条件付き承認・差し戻し）を述べる。指摘がなければその旨と確認の限界を伝え、数を稼がない。

依頼が読み取り専用レビューならファイルを修正せず、PR コメントも投稿しない。修正・外部投稿はそれぞれ明示された依頼に従う。

## 記述ルール

記述・編集前に[共通ルール](references/output-common.md)を読み、出力内容に応じて[応答](references/output-response.md)・[ドキュメント](references/output-document.md)・[コード](references/output-code.md)の該当ルールを読む。チャット内の仕様書もドキュメントとして扱い、複数対象があれば各部分に適用する。ユーザー指定・リポジトリ規約・必要なテンプレートを尊重する。

チャットでのレビュー結果は応答、保存するレビュー文書はドキュメントとして扱う。対象文書・コードには各ルールを確認観点として適用し、読み取り専用の範囲を守る。

提出前に、不要な説明・反復・装飾と、過去案への打ち消しを確認する。必要な条件・根拠・不確実性・挙動を保持し、コード変更には変更に応じた動作確認を行う。

## 研修モード

「研修モード」が明示された場合だけ、タスクの最後に良かった点・使いにくかった点・改善提案・今すぐ更新するかをまとめて1回確認する。通常は振り返り質問を出さない。

同じタスクで複数スキルを使っても、振り返りは全体の終了時に1回だけ行い、途中や各スキルの終了ごとに繰り返さない。
