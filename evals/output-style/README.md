## 修正した問題

初回の運用文書は、未検証の重複取得から「取得済み範囲を確認できるまで再実行を保留する」という新しい運用方針を確定していた。元資料にない操作方法も補っていた。

共通ルールに方針・手順の保持を明記し、文書ルールに、資料にない操作方法や判断条件を確認事項として扱う指示を追加した。再評価では、現行手順と未確認の操作情報を分け、新しい停止条件を確定しなかった。コミットメッセージに元の抽象表現を再掲する冗長さも修正対象に加えた。

## 成果物

元資料と依頼は [cases.md](cases.md)、実際の出力は [outputs/](outputs/) に保存した。`document-A-initial.md` が修正前、`document-A.md` と `document-B.md` が修正後の再評価出力。応答とコードは初回評価の出力を保持している。

コードは独立評価側で変更前後の12項目ずつを確認した。加えて親エージェントが変更後の実装について、公開引数、不正入力、戻り値の同一性、再試行回数、待機・警告回数、例外の同一性、単一試行、待機0、回避策のコメント、参照ファイルの未変更を16項目確認した。詳細は [code-checks.txt](outputs/code-checks.txt)。

再実行用に [check_retry.py](check_retry.py) を同梱した。リポジトリ直下で `python -B evals/output-style/check_retry.py` を実行すると、入力例と編集後の実装に同じ12テストを適用する。

別の評価者が元資料・現行出力・変更前コードを照合し、この24テストを再実行した。修正後の成果物に、公開を止める問題または修正が必要な問題は見つからず、判定は承認となった。

## 再評価方法と限界

`cases.md` のケースを、会話の背景や期待する出力を渡さずに実行する。記載したスキルのフォルダだけを評価用ディレクトリにコピーし、スキルと必要な参照を読ませる。コードは入力例のコピーだけを編集させ、元の入力に対する挙動と比較する。

件数・日時・制限・不確実性が保持されたか、資料にない方針を追加していないか、出力の種類を正しく選べたかを元資料と照合する。コードでは必要な挙動を実行して確かめる。語句の出現数や短さだけを合格基準にしない。

架空の5ケースによる適合確認であり、ルールなしとの比較実験や、全モデル・全ホストでの検証ではない。共通ルール修正後の実出力再評価は文書2ケースに対して行った。チャット内の手順書は確認したが、Workの画面操作や専用の配布・実行環境は検証していない。
