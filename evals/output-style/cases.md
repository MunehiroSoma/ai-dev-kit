# 評価用の依頼と資料

すべて架空の資料。評価時は対象ケースとスキルのパスを渡し、外部への投稿や評価フォルダ以外の編集を行わない条件で実行する。

## 応答A（long-run）

依頼: 長時間のCSV取り込みについて「今どうなっていますか？」に返答する。

資料: 入力120件、完了117件、保留3件。保留は会社コード未登録。117件は保存先DBで照合済み。担当者へのコード確認が必要。処理時間23分。Python起動・UTF-8確認・接続確認は成功、10件ごとに進捗ログあり。旧案の手動コピー方式は採用せず、管理画面も入れない。「ログを正本として証跡の整合を担保した」という表現がある。コード登録が間違いの原因という点は未検証。

## 応答B（long-run）

依頼: 担当者向けの手順を書き、ユーザーが次にすることも一言添える。

資料: 管理ツールの「取り込み」で入力CSVを選択。実行前に会社コードの登録を確認。実行後に件数とエラーログを確認。失敗行は原因を直して再実行。二重取り込み防止のため実行中は同じCSVを再実行しない。旧手順では共有フォルダにCSVをコピーしていた。前案の専用画面は作らない。ユーザーの次の行動は会社コード一覧の確認。

## 文書A（create-issue）

依頼: 手元の資料から担当者向けREADMEの運用手順と、別記のコミットメッセージ草案を作る。

資料: 毎平日8:30 JST、Windows Task Schedulerから取得ジョブ実行。祝日も平日なら実行。取得元APIは読み取り専用。ログは `logs/fetch-YYYYMMDD.log`。タイムアウト60秒。失敗時は担当者がログ確認後に手動再実行。旧手順はCSV手動コピー。前案の管理画面は取りやめ、Pullによる自動更新は入れない。本番DBへの書き込み禁止。同じジョブの同時実行禁止。API上限500件/回なので600件入力は分割が必要。再試行で重複取得しないことは未検証。「正本の証跡から整合性を担保し運用の解像度を上げる」という表現がある。経緯はコミットメッセージに残す。

## 文書B（create-issue）

依頼: 次のBug Issue草案のタイトルと本文を整える。投稿は行わない。

資料: 「革命的な安定性を実現するための非常に重要な改善」という冒頭。失敗ログを画面から確認できない。データが全部消えたかもしれないが未確認。2026-10-18、120件中117件完了、3件保留。ログを手動確認すると会社コードが見つからないことが理由と分かる。期待する挙動は、結果画面に保留件数と行別理由を表示すること。完了条件は未登録会社コードのCSVで件数と理由が表示され、正常行117件の処理が継続すること。前案の自動補完機能は入れない。原因をユーザーのCSVと断定できない。関連Issueとラベルは不明。
